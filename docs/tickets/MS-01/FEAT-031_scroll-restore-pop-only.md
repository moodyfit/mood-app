# FEAT-031: 스크롤 복원을 "뒤로가기(POP)"일 때만

## Problem

소피 피드백(2026-11-19, PWA 실기기 테스트): 하단 탭으로 화면을 옮길 때마다 스크롤이 이전
위치로 복원되는 게 어색하다. 지금 `useScrollRestore`는 "어떻게 들어왔는지"를 전혀 안 보고,
sessionStorage에 저장값이 있으면 무조건 복원한다.

소피 제안:
- 목록 → 상세 → 뒤로가기: 지금처럼 복원
- 하단 탭 이동: 복원 안 함, 맨 위에서 시작
- 새로고침: 맨 위에서 시작

세 번째 항목은 BUG-014(새로고침 스크롤 복원 버그)를 "제대로 복원하기"가 아니라 "애초에 복원
시도를 안 하기"로 더 근본적으로 해결한다 — BUG-014의 pathname 기반 수정이 여기에 흡수될
가능성이 있음(머지 순서·중복 여부 확인 필요).

## 기술적 난점

Next.js App Router에는 "이 마운트가 뒤로가기(POP)로 왔는지 탭 클릭(PUSH)으로 왔는지"를 주는
공식 API가 없다. Performance Navigation Timing API(`reload`/`back_forward`/`navigate`)는
풀 페이지 로드 기준이라 클라이언트 사이드 라우트 전환에는 적용 안 됨.

필요한 건 `popstate` 이벤트(브라우저 실제 뒤로가기·forward에서만 발생, `router.push`/`<Link>`
클릭에서는 미발생)를 직접 리스닝해서 "마지막 네비게이션이 POP였는지" 신호를 만드는 것.

## Scope(초안)

- 전역에서 한 번 `popstate` 리스너를 달아 "마지막 네비게이션 = POP" 신호를 추적(모듈 스코프
  플래그 또는 작은 전역 훅).
- `useScrollRestore`의 복원 effect가 이 신호를 같이 보게 수정 — POP가 아니면 저장값이 있어도
  `scrollTo`를 아예 시도하지 않는다(= 맨 위에서 시작, 새로고침도 포함).
- 저장(write) 쪽 로직은 그대로 — 어차피 복원 여부만 바뀌는 거라 저장을 막을 이유는 없음.
- 기존 레이스 방지 로직(BUG-004/008/011/014 — restoredRef, 디바운스, pathname 체크)이 이
  변경과 안 부딪히는지 하나씩 재확인 필요. 특히 BUG-014의 pathname 가드는 이 변경이 들어가면
  역할이 줄어들거나(POP 신호가 더 정확한 상위 조건이 되므로) 아예 필요 없어질 수 있음 — 확인
  후 정리.
- 영향 범위: `HomeGallery.tsx`, `PhotoGrid.tsx`, `ResultsGrid.tsx` 전부(같은 훅 공유).

## Verification 기준(초안)

- 하단 탭으로 화면 이동 → 맨 위에서 시작(스크롤 복원 안 됨).
- 목록에서 스크롤 내린 뒤 카드 클릭 → 상세 → 뒤로가기 → 그대로 복원(기존 동작 유지).
- 새로고침(어느 스크롤 위치에서든) → 맨 위에서 시작.
- `tsc --noEmit`, `npm run build` 통과.
