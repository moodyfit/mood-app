# BUG-014: 맨 위로 스크롤한 뒤 페이지를 떠났다 돌아오면 예전(아래) 위치로 복원됨

## Problem

2026-11-16 회의록: "새로고침 시 스크롤 위치가 달라짐 — 메인 페이지에서 스크롤 위로 올린 후
맨 위에서 새로고침하면 아래 스크롤로 내려가는데".

사용자 추가 재현(1차 수정 후에도 남아있던 경로): 새로고침은 고쳐졌지만, **스크롤 내림 → 맨
위로 올림 → 맨 위 카드 클릭 → 뒤로가기**를 하면 똑같이 아래 위치로 복원됨.

## 원인

`useScrollRestore.ts`의 onScroll 저장 로직이 `scrollY<=0`인 이벤트를 저장하지 않았다
(BUG-011 — 사진 클릭→상세 이동 시 Next.js가 일시적으로 스크롤을 0으로 리셋하는 걸 실제
위치로 착각해 저장해버리는 레이스를 막기 위함). 그런데 이 가드는 "네비게이션이 만든 리셋(0)"과
"사용자가 진짜로 맨 위까지 스크롤한 것(역시 0)"을 값만으로는 구분 못 해서, 후자도 똑같이
막아버렸다 — sessionStorage엔 스크롤을 내렸을 때의 낡은 값이 계속 남아 있었다.

1차 수정(`pagehide`에서 무조건 저장)은 새로고침·탭 닫기 경로는 고쳤지만, "클릭→뒤로가기"는
SPA 클라이언트 사이드 네비게이션이라 `pagehide`가 아예 발생하지 않아 그대로 남아있었다.

## Fix

가드 기준을 "스크롤 값이 0인지"에서 "그 사이에 실제로 다른 페이지로 이동했는지"로 바꿨다.
`usePathname()`으로 타이머를 스케줄링한 시점의 pathname과 실제 발화 시점의 pathname을
비교해서, 다르면(네비게이션 진행 중) 저장을 버리고 같으면(진짜 유휴 상태, 0이어도) 그대로
저장한다. 이러면:
- BUG-011의 원래 레이스(네비게이션 중 리셋값 저장)도 계속 막힌다 — 네비게이션 중엔 pathname이
  이미 바뀌어 있다.
- 사용자가 진짜로 맨 위에 머무른 경우는 pathname이 안 바뀌었으니 0도 정상적으로 저장된다.

`pagehide` effect(1차 수정)는 디바운스(200ms)가 끝나기 전에 새로고침하는 극단적 케이스를 위한
안전망으로 그대로 둔다.

## Verification

Playwright로 재현:
- 휠로 스크롤 다운(3000px) → 휠로 맨 위까지 스크롤 업 → `sessionStorage`에 `scrollY:0`으로
  정확히 갱신되는 것 확인(수정 전엔 낡은 3000이 남아있었음).
- 맨 위 카드 클릭(상세 페이지로 이동) → 뒤로가기 → `scrollY` 0 유지 확인(수정 전엔 3000으로
  복원됐을 경로).
- `tsc --noEmit`, `npm run build` 통과.
